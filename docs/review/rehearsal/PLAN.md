## リハーサルの目的（レビューとの違い）

「レビュー」= ドキュメントの整合性・抜け漏れを観察者視点で点検
「実装リハーサル」= **このドキュメントだけを頼りに実際にデプロイ作業を行うつもり**で読み進め、実装者として詰まる箇所・判断に迷う箇所・実行不能な箇所を抽出

## 4 つの検証観点

| 観点 | 具体的な問い |
|---|---|
| 1. 手順の実行可能性 | 書いてある通りに実行して詰まるか？ コマンド・ファイルパスは正確か？ |
| 2. 情報の十分性 | 判断に迷う曖昧な記述はないか？ 「適切に」「必要に応じて」等の曖昧語に具体性はあるか？ |
| 3. 設定値の整合性 | 各 FR/タスクの設定例（バージョン、フラグ、パス）に矛盾はないか？ |
| 4. テストの実行可能性 | テストを実際に実行できるか？ コマンド・期待値・判定基準は明確か？ |

## 各ラウンドのスコープ（Phase 別の実装リハーサル）

| Round | スコープ | 観点 |
|---:|---|---|
| 1 | 要件確認 → Phase 0/1（フィールド対話・scaffold 起動） | 手順実行可能性・情報十分性 |
| 2 | Phase 2/3（parser 実装・rules 作成） | 設定整合性・情報十分性 |
| 3 | Phase 4（3 層 E2E テスト） | テスト実行可能性 |
| 4 | Phase 5/6（build / release / 運用 / SBOM・署名） | 手順実行可能性・設定整合性 |
| 5 | 全章通読・最終 sanity・収束評価 | 4 観点全て |

## 出力

- `docs/review/rehearsal/round{N}.md` … 各ラウンドの実装リハーサル所見と修正
- `docs/review/rehearsal/convergence_report.md` … 5 ラウンドの修正件数推移と収束評価
- GitHub Issue #1 にコメントで進捗

## 修正対象の選定基準

リハーサル中に「**実装者として手が止まる**」と判断したら修正対象とする：
- ファイルパスが具体名で書かれていない（「適切な場所」等）
- コマンドの引数・フラグが省略されている
- 「設定値」が範囲（「100ms 〜 1s」等）で具体的初期値がない
- テストの **期待出力** が示されていない
- 前提となるコマンド（インストール、初期設定）が抜けている

純粋なレビュー観点（タイポ、表現整理、章番号）は対象外（前ラウンドのレビューで対応済み）。

## ルール

- 修正は要件 v3 / 詳細タスク定義書を直接 Edit
- 修正前後で意味が変わらないか確認
- 件数を round{N}.md に列挙し、convergence_report.md で集計
