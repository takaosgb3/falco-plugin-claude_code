対象: Round 1+2+3 適用済みの本書
観点: 残課題、抜け漏れ補完、誤り訂正

## A. 受入完了判定の不完全性
- §8.6 で R3-08 により E4（互換性）は項目 11 として追加された。しかし、要件 v2 §E5（性能）/§E6（セキュリティ）/§E7（テンプレート変数仕様）への明示的な確認項目がない。
- E5「100 events/sec」は AT-5/TC-5-01 で確認（既存項目 2 で含意）。
- E6「ReDoS 防止 / nil map / 入力長 / パストラバーサル」は T1-1, T2-1, T5-1 で対応するが §8.6 で明示なし。
- E7「テンプレート変数仕様」は T4-1, T5-4 で対応。AT-1〜3 の生成成功が間接確認だが §8.6 で明示なし。
- **修正対象 (R4-01)**: §8.6 既存項目 10「ドキュメント整合性」を「ドキュメント整合性 + §E1〜E8 全要件確認」に拡張、または個別項目を追加。

## B. test-plugin の標準化
- §1.5.3 で「テスト用プラグイン test-plugin を生成」と記載されているが、各 Step で同じ test-plugin を再利用するのか毎回再生成するのか不明。
- §2.3 T1-1 検証で `/tmp/test-plugin` を新規作成しているが、§3.3 T2-1 では「テスト用プラグインで」とだけある。
- **修正対象 (R4-02)**: §1.5.3 で「Step ごとに新規生成して clean state を維持」と明示。

## C. 既存プラグインへの回帰確認の前倒し
- §8.1.2 PR-2 と §8.3.1 で nginx-plugin / openclaw への破壊的変更を懸念しているが、回帰確認は「v0.2 移行」と書かれており **dev-kit v2 では実施されない**。これは PR-2 リスクが高（影響: 高）であるにも関わらず対策が将来に丸投げされている。
- 各 Step 完了時に既存プラグインの go vet/test を実施するのが安全。
- **修正対象 (R4-03)**: §8.2.2 拡張受入テストに ET-7 として「既存プラグイン（nginx-plugin / openclaw）の go vet/test 回帰確認」を追加。実施タイミングを §8.2.3 にも反映。

## D. T2-5 と要件 v3 §18.4 の食い違い解消の責任所在
- Round 3 で dev-kit Pコード ≠ 要件 v3 §18.4 解釈の食い違いが 8 件あることが明示された。
- ただし、誰が・いつ・どう解消するかが本書に未明記。T2-5 が原典 PROBLEM_PATTERNS.md の集約タスクなので、ここで認識し別 Issue 化するのが自然。
- **修正対象 (R4-04)**: §3.7 T2-5 完了基準に「要件 v3 §18.4 との Pコード意味食い違い 8 件の整合プランを別 Issue（claude-code 側）で起票」を追加。

## E. T1-3 の TC 表記

## F. 主要リポジトリの場所表

## G. 改訂履歴の追従
